# 9. Drop MariaDB — DuckDB becomes the system of record

- **Status:** Accepted; implemented (2026-07-26)
- **Date:** 2026-07-26

## Context

ADR 0008 introduced DuckDB as a read-only, derived analytics cache: MariaDB stayed
the system of record, ingestion wrote raw rows there, and a per-cycle refresh copied
those rows into DuckDB for leaderboard/player-detail queries to aggregate on the fly.
Phase 3 of that migration (retiring the pre-aggregated tables and stored procs)
shrank MariaDB's remaining job to almost nothing: EF Core touched it for exactly 4
write call sites (insert a game graph, upsert players, update player profiles) and
one read (the player list, the only endpoint DuckDB didn't already serve).

At that size, running two databases stopped paying for itself. The dataset itself is
small — 43 MB, ~15k games, ~1k players — and the backend already co-hosts ingestion
and the API in one process (ADR 0006), so DuckDB's single-writer limitation, normally
the reason to keep a "real" database around, costs nothing here. Keeping MariaDB
meant carrying a 435 MB container, the `mysql` scanner extension and its runtime
download from `extensions.duckdb.org`, a full-table-rebuild copy step every ingestion
cycle, and two SQL dialects — to serve four write calls and one read.

## Decision

DuckDB is now the **only** database. Ingestion writes land directly in DuckDB's raw
tables (`Players`, `Games`, `PlayerStats`, `ClassStats`, `WeaponStats` — schema in
`TF2SA.Data/Analytics/Schema.sql`, self-initializing via `CREATE TABLE IF NOT
EXISTS`), and every read — leaderboards, player detail, comparison, and now the
player list — queries those same tables. There is no more refresh step: a write is
immediately visible to every read, since there is nothing to copy from anymore.

- **Surrogate keys** (`PlayerStatsID`/`ClassStatsID`/`WeaponStatsID` — the three
  columns MariaDB auto-incremented) are generated by DuckDB sequences
  (`nextval('seq_playerstats')` etc.) and threaded down through the insert graph by
  hand in `LogIngestionRepositoryUpdater`, replacing EF's automatic FK fixup.
  `Games.GameID` and `Players.SteamID` are unaffected — always caller-supplied from
  logs.tf/Steam data, exactly as before.
- **The `GameLog` → row mapping** that used to go through AutoMapper's
  `GameMappingProfile` is now hand-written (same reasoning as below — see
  Consequences). It produces the same flattening of `LogInfo`/`Uploader` onto `Game`,
  the same Red/Blue score lookup, and the same numeric narrowing AutoMapper's
  nullable-to-non-nullable convention used to apply.
- **The EF select-then-insert race** on player upsert (a commented, known issue —
  two concurrent logs introducing the same new player could both pass the
  "not existing" check) is closed as a side effect, not a separate fix: every write
  now serializes through the store's single-connection semaphore, and the upsert
  itself is one `INSERT ... ON CONFLICT (SteamID) DO NOTHING` per player.
- **EF Core, Pomelo, and AutoMapper are removed entirely** — not just their MariaDB
  usage. AutoMapper's remaining read-side maps (10 leaderboard row types, 3
  player-detail row types, all flat/same-shape) became hand-written `ToDomain()`
  extensions (`TF2SA.Data/Mapping/DomainMappingExtensions.cs`), the same pattern
  already used for the HTTP layer. This also clears the suppressed AutoMapper
  advisory `GHSA-rvv3-g6hj-g44x` (`Directory.Build.props`, now deleted) — there's
  nothing left to suppress.
- **This supersedes [ADR 0004](0004-database-first-ef-scaffolding.md)** (database-first
  EF scaffolding — no EF, nothing to scaffold) and updates the system-of-record
  framing in [ADR 0008](0008-duckdb-analytics-read-layer.md): DuckDB was introduced
  there as a derived cache; it is now the source of truth. ADR 0008 itself stays as
  the record of *why* DuckDB was chosen — that reasoning (columnar, in-process,
  no separate service) holds regardless of which side of the read/write line it sits on.
- **Deployment**: `docker-compose.yml` drops the `tf2sa-db` service; `tf2sa-backend`
  gets a host bind mount for the DuckDB file instead of MariaDB's anonymous
  container-layer storage. A bind mount, not a named volume, so `docker-compose down
  -v` — already a known risk, run on every deploy — can no longer touch the database
  at all (see [deployment.md](../architecture/deployment.md)). A small
  `scripts/backup-duckdb.sh` covers periodic backup, since the file is now
  load-bearing rather than a rebuildable cache.

## Consequences

- **One database, one SQL dialect, one write path.** No more refresh step, no more
  `mysql` scanner extension, no more parallel-run branch in every handler.
- **DuckDB is load-bearing now.** Its persistence matters, unlike ADR 0008's
  "rebuildable cache" framing — mitigated by the bind mount (survives `down -v`) and
  the backup script, and softened by the fact that all data is ultimately
  re-derivable from logs.tf's own history if both were ever lost.
- **The write path lost EF's automatic graph-insert/FK-fixup convenience.**
  Multi-table inserts and surrogate-key generation are now explicit, hand-written
  code (`DuckDbAnalyticsStore.InsertGameAsync` and its row-insert helpers) rather
  than "attach a `Game` object graph and call `SaveChanges`." This is more code, but
  it is code the team fully owns and can read top to bottom, with no ORM tracking
  behaviour to reason about — a trade already made once for the read side in ADR 0008.
- **All writes are parameterized** (`DuckDBCommand.Parameters`, never string
  interpolation) — a deliberate discipline, since unlike the read-side macros (which
  only interpolate internally-whitelisted identifiers) this path persists real
  user-influenced text: player names, map names, log titles.
- **A real, disclosed behaviour change**: the player list's default sort order for
  symbol-prefixed names shifted, because MariaDB's `utf8mb4_unicode_ci` collation
  (which weights punctuation near-last) is gone along with MariaDB — DuckDB orders
  `VARCHAR` by plain codepoint. Not a bug; noted in
  [known-issues.md](../known-issues.md).
- **One-time production migration is an operational step, not app code**: a `.sql`
  script run once via the DuckDB CLI, reusing the exact `ATTACH ... TYPE mysql` +
  `CREATE TABLE AS SELECT` mechanism ADR 0008's own refresh used, documented in
  [deployment.md](../architecture/deployment.md) rather than shipped as throwaway
  migration code that would need deleting immediately after use.
- **Verified, not assumed**: the new write path was checked against MariaDB's
  existing data before any of this shipped — 100 real games ingested through the new
  path into a scratch file, diffed row-for-row against MariaDB's stored data for
  those same (already-ingested) GameIDs across all 5 tables, zero mismatches. The
  full stack (schema self-init, ingestion, every read endpoint) was also run inside
  the actual Docker image with no MariaDB reachable at all.
